0.1 编译与链接：你的代码经历了什么

在写出第一行 C++ 之前，有一个问题值得先想清楚：计算机真正执行的，并不是你写的那些文字。CPU 只认识机器码（一串数字），而你写下的是接近英语的文本。那么中间发生了什么？

这一节我们就来跟踪一份源代码的"旅程"。理解了这段旅程，你以后遇到报错时，就能立刻判断：这个问题出在哪一站？——这是初学者最需要建立的直觉。

一段代码的五站旅程

① 编写 .cpp
② 预处理器
③ 编译器 → .o
④ 链接器 → 可执行文件
⑤ 运行

下面逐站展开。每站讲清楚三件事：它做什么、输入输出是什么、你在这一站会见到什么报错。

第 ① 站：编写源代码

你用编辑器写出 .cpp 文件——这是纯文本，任何人用记事本都能打开。此刻它还不是程序，只是一份"给编译器的说明书"。这一站没有报错，但有一个习惯值得立刻建立：每写完一个小功能就编译一次，不要写满 500 行才第一次按下编译键——那样一次会涌出几十个报错，而且后面的报错多半是前面的错误"连坐"出来的假错误。

第 ② 站：预处理器（preprocessor）

做什么：对源码做纯文本级别的加工。它不懂 C++ 语法、不懂变量、不懂类型——它只认识以 # 开头的指令（如 #include、#define），逐条执行"查找替换、文件粘贴"这类机械操作。

输入输出：输入是你的 .cpp；输出是"展开完毕的翻译单元"——所有 #include 的文件内容已被原样粘贴进来。这才是编译器真正看到的东西。

典型问题：这一站几乎没有"报错"概念（它太机械了），但错误操作会让后面炸锅——比如 #include 了不存在的文件直接报 file not found。想亲眼看看它的产物？g++ -E main.cpp 会把预处理后的结果打印出来（第 2 章有专门的练习）。

第 ③ 站：编译器（compiler）

做什么：把翻译单元逐个翻译成机器码，同时做严格的语法与类型检查。注意"逐个"——编译器每次只看一个翻译单元，对其他 .cpp 文件的存在一无所知（这就是"翻译单元"定义的由来，见下方概念框）。

输入输出：一个翻译单元进，一个目标文件（.o / .obj）出。目标文件里已经是机器码，但"调用了别处函数"的位置暂时是空着的占位符。

典型报错：你未来见到的绝大多数报错都在这一站——语法错误（少了分号）、类型错误（用 double 初始化 int）、名字未声明（'add' was not declared）。它们有个统一特征：报错时会给出文件名和行号，因为编译器精确知道自己在哪个文件的哪一行卡住了。

第 ④ 站：链接器（linker）

做什么：把所有目标文件 + 库（比如标准库）拼装成一个可执行文件。核心工作是"对号入座"：每个目标文件里都有一些"我要调用 add"的占位承诺，链接器在所有目标文件里找到 add 的实际函数体，把真实地址填进去。

输入输出：所有 .o 文件 + 库 进，一个可执行文件出。

典型报错：undefined reference to 'add(int, int)'（承诺了但全程序没人定义）或 multiple definition（同一个函数定义了两份）。特征：没有行号——因为问题不在某个文件的某一行，而在"文件之间的关系"（名字对不上、文件清单漏了）。

第 ⑤ 站：运行

做什么：操作系统把可执行文件加载进内存，从 main 开始执行。

这一站的问题最难查：程序能跑起来，说明编译链接都过了，但运行时的行为可能不对——输出错误、崩溃、甚至"看起来正常但结果是错的"。编译器和链接器都帮不了你了，需要调试器（第 3 章的主角）。另外还有一种特殊类别叫未定义行为：程序可能有 UB 但运行"一切正常"，换个编译器/换台机器就炸——第 1 章会第一次撞上它。

站点输入 → 输出报错特征
② 预处理器.cpp → 翻译单元文件找不到（file not found）
③ 编译器翻译单元 → .o有文件名和行号，语法/类型问题
④ 链接器所有 .o + 库 → 可执行文件无行号，名字对不上/找不到定义
⑤ 运行可执行文件 → 行为无报错信息，需要调试器；警惕 UB
📐 概念

翻译单元（translation unit）：一个 .cpp 文件经过预处理后的整体。编译器每次只看一个翻译单元——它不知道其他 .cpp 文件的存在。

目标文件（object file，.o / .obj）：单个翻译单元编译出来的机器码。它已经是"机器语言"了，但还不能独立运行——因为它可能引用了别处的函数。

链接器（linker）：把所有目标文件和库"缝合"在一起，把每个"我要调用某函数"的承诺兑现成真实地址，产出最终可执行文件。

一个关键的设计：编译和链接是分开的

为什么不像 Python 那样直接执行源码，而要拆成两步？看这个例子：

int add(int x, int y);        // 只承诺："存在一个 add 函数"

int main()
{
    return add(3, 4);         // 编译器：好的，你说过它存在，我信了
}

main.cpp —— 注意 add 只有声明，没有函数体

编译 main.cpp 时，编译器看到 add(3, 4)。它并不需要知道 add 怎么实现——它只需要知道"有这么个函数、参数是什么类型、返回什么类型"，就能生成"跳转到 add"的机器码，至于 add 在哪，留给链接器去填。

这就是分工的本质：

编译器链接器
视野单个翻译单元所有目标文件 + 库
职责语法、类型检查，生成机器码把"函数名"对接到"函数体"
典型报错error: 'add' was not declaredundefined reference to add(int, int)

选择你写了两个文件：main.cpp 调用了 int add(int, int)，add.cpp 定义了它。编译时你不小心把 main.cpp 里的声明写成了 int addNum(int, int)（而调用处也写的是 addNum）。会发生什么？

从反例中理解：两种报错，两种修法

⚠️ 反例 1：编译错误（编译器拦下你）
int main()
{
    retrun 0;   // 拼写错误
}

编译器当场报错：'retrun' was not declared in this scope。程序根本不会诞生——这是好事，错误被拦在了最早的一站。

⚠️ 反例 2：链接错误（链接器拦下你）
// main.cpp
int add(int x, int y);   // 声明了……

int main()
{
    return add(1, 2);    // ……但整个程序里没人定义它
}

编译通过！因为编译器"信了"你的声明。但链接器翻遍所有目标文件，找不到 add 的函数体：undefined reference to 'add(int, int)'。

判断"看到 undefined reference 就说明我的函数名拼错了。"

库：别人写好的目标文件的集合

你从没写过"往屏幕上打印字符"的代码，但 std::cout 却能用——因为标准库里已经有人写好了，链接时自动接上。库本质上就是"打包好的目标文件 + 声明清单"。

💭 思维转变

初学者把报错当失败；有经验的人把报错当导航。看到编译错误，你知道去检查当前文件的语法类型；看到链接错误，你知道去检查名字一致性和文件列表。报错的"站点"信息本身就是调试线索——第 3 章调试会大量用到这一点。

本节小结

  • 源代码 → 预处理 → 编译（逐翻译单元）→ 链接（跨文件拼装）→ 运行
  • 编译器只需要声明就能放行调用；定义可以后给、别处给
  • undefined reference = 链接器找不到定义 → 检查名字/签名/文件列表

🎯 预测输出：main.cpp 声明并调用 add(3, 4)，add.cpp 定义 return x + y;，两文件编译链接后运行，输出什么？
