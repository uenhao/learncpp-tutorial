0.2 构建配置与语言标准

上一节你跟踪了一段代码的五站旅程。这一节讲一件实际操作层面的事：同样的旅程，可以按不同的"配方"走。配方决定两件事：程序为谁优化，以及编译器按哪一版 C++ 规则理解你的代码。

构建配置是什么：一个你可能天天见却没注意的选项

"构建配置（build configuration）"听起来抽象，但它其实就是一个具体的开关。在本项目的 VS Code 里（装了 CMake Tools 扩展后），打开任何一个 .cpp 文件，看窗口底部状态栏：会有一项显示当前的构建变体，默认是 CMake: [Debug]——点它就能在 Debug / Release / MinSizeRel / RelWithDebInfo 之间切换。在命令行里，它则对应你传给 CMake 的 -DCMAKE_BUILD_TYPE=Debug 参数。

换句话说：构建配置 = 一组预设的编译器参数。你不需要每次手敲一长串选项，而是选一个预设名字，CMake 就知道该给编译器带上哪些参数。最重要的两套预设，就是 Debug 和 Release。

Debug 与 Release：同一份代码的两种人格

两套预设到底差在哪？先看它们各自"翻译成命令行"是什么样子：

# Debug 配置实际上相当于：
g++ -std=c++20 -g -O0 -o prog main.cpp

# Release 配置实际上相当于：
g++ -std=c++20 -O2 -o prog main.cpp

这些以 - 开头的词叫编译器选项（flag）。逐个拆解——注意 g++ 的选项几乎都是英文单词的缩写，知道全称就再也不会记混：

选项缩写自含义
-std=c++20standard指定按哪一版 C++ 标准编译（= 后面跟标准名）
-ggdb / debug把调试信息（源码行号 ↔ 机器码的映射表）写进可执行文件，gdb 等调试器靠它工作。文件会明显变大
-O0 / -O2Optimization + 数字优化等级：-O0 不优化（最快编译、行为最"直白"）；-O2 是常用的发布级优化；还有 -O3 更激进、-Os 为体积优化
-o progoutput指定输出文件名（这里是 prog）。注意是小写 o，和优化的大写 O 是两个东西！
main.cpp——要编译的源文件（不是选项）

两个最容易踩的坑，题目里见分晓：

选择g++ 的优化选项 -O2 和输出选项 -o，如何区分？

看懂了这些参数，两套配置的定义就好理解了：

📐 概念

Debug 构建：不做优化（-O0），并嵌入调试信息（-g）。不做优化意味着程序按你写的顺序、一步一步执行，每个变量都真实存在于内存里——调试器才能让你打断点、单步执行、查看变量。调试信息则记录"机器码第几条对应源码第几行"这类映射，让调试器能把两边对上。这是给你自己（开发者）用的配置。

Release 构建：开优化（-O2），不嵌调试信息。编译器被允许重排语句、内联函数、消除"算出来没人用"的代码——一切为了让最终程序快而小。这是给用户用的配置：用户不需要调试你的程序，只需要它跑得快。

一句话总结分工：Debug 给人调试用，Release 给人使用。这也直接回答了"该用哪个"：写代码、找 bug 时用 Debug；确认没问题、要交付或测性能时用 Release。

现在回到"优化"到底做了什么。想想这个函数：

int square(int x)
{
    return x * x;
}

int main()
{
    int width{ 5 };
    int height{ 8 };
    int area{ square(width * height / 2) };
    std::cout << area << '\n';
}

Debug 模式下，程序老老实实地：创建 width、创建 height、调用 square、返回 400、存进 area、打印。每一步都真实发生。

Release 模式下编译器"一眼看穿"：width、height 是常量，square(20) 恒等于 400，于是整个计算在编译期就完成了，运行时只剩一条"打印 400"。width、height 这些变量在可执行文件里根本没有存在过。

这就是双重含义所在：

  • 好处：同样的功能，程序更快、文件更小；
  • 代价：在 Release 下用调试器查看变量，会看到 <optimized out>——变量被优化掉了，物理上不存在，调试器无从展示。这就是为什么调试必须用 Debug 构建。

选择你的程序在 Debug 下运行结果正确，在 Release 下偶尔崩溃。最可能的解释是什么？

语言标准：你的代码说的是哪一年的 C++

C++ 大约每三年发布一个新标准：C++11 → 14 → 17 → 20 → 23。标准决定了"哪些写法合法"。问题在于：很多编译器默认标准偏旧（比如不少 g++ 默认 C++17），你写了 C++20 的语法却忘了告诉编译器，就会得到莫名其妙的报错。

# 显式指定标准 —— 养成习惯
g++ -std=c++20 -Wall -Wextra -o prog main.cpp

# 查看编译器实际用的标准
g++ -dM -E - < /dev/null | grep __cplusplus
# 201709L = C++17、202002L = C++20（仓库 chapter0/04-language-standard/check_standard.cpp 可直接运行验证）
✅ 最佳实践（learncpp 原文强烈强调）
  • 始终显式指定 -std=c++20（或项目统一的标准），不要依赖编译器默认值
  • 开发用 Debug 配置；发布/测性能用 Release
  • 永远开 -Wall -Wextra，把警告当 bug 对待

判断"警告（warning）不是错误（error），所以可以放心忽略。"

💭 思维转变

"在我机器上是好的"（Works on my machine）之所以成为经典梗，根源就在构建配置：不同的人用了不同标准、不同优化等级、不同警告级别，UB 在不同环境里发作方式不同。把配置写进构建脚本（如 CMake）而不是口头约定，就是为了让所有人的"配方"完全一致——本项目根目录的 CMakeLists.txt 就在做这件事。
