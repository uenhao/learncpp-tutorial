15.3 友元与进阶：给封装开一扇受控的门

private 是墙（14 章）。但有时墙太严：两个类天生要配合（点与向量、存储与显示器），隔着墙只能堆 getter。friend 让类自己决定把钥匙发给谁——门还是那扇门，名单由类掌控。（原文 15.8–15.10）

友元非成员函数（friend non-member functions）

📐 概念：friend declaration

friend（友元） = 被授予"完全访问另一类 private/protected 成员"权限的类或函数。在类体内用 friend 声明：

class Accumulator
{
    int m_value{ 0 };

public:
    void add(int value) { m_value += value; }

    friend void print(const Accumulator& accumulator); // friend 声明
};

void print(const Accumulator& accumulator)  // 普通非成员函数
{
    std::cout << accumulator.m_value;  // ✅ friend：可访问 private
}
  • Key insight：friendship 由"被访问成员的类"授予，不是谁想要就能拿——访问控制 + 发证权都在类手里，数据隐藏没有被破坏；
  • friend 声明不受访问级别影响（放 private 区也一样生效）；
  • friend 非成员函数没有隐式对象——对象必须显式传参（它是普通函数！）；甚至可以在类体内定义（仍然是非成员函数）；
  • 一个函数可以是多个类的 friend；声明里用到未定义的类需要类的前置声明（class Humidity;）。

判断① "print() 成了 Accumulator 的 friend，调用它时也有隐式对象——acc.print() 这种写法合法。"

✅ 最佳实践（原文）

friend 函数能走类接口就别直访成员；能不当 friend 就不当（加一个合理的 access function 常常就够了）。friend 直接触碰实现 → 类一改实现，friend 跟着遭殃。friendship 的正当场景：两个类紧密协作（如容器与它的迭代器）、为运算符重载铺路（21 章）。

友元类（friend classes）

📐 概念：friend class

把整个类设为 friend——它的所有成员函数都能访问本类的 private：

class Storage
{
    int m_nValue{};
    double m_dValue{};

public:
    Storage(int nValue, double dValue)
        : m_nValue{ nValue }, m_dValue{ dValue } {}

    friend class Display;  // Display 的所有成员函数获得访问权
};

class Display
{
    bool m_displayIntFirst{};

public:
    void displayStorage(const Storage& storage)
    {
        std::cout << storage.m_nValue << ' ' << storage.m_dValue; // ✅
    }
};

三条纪律（原文要点）：friendship 不互惠（Display 是 Storage 的 friend ≠ 反过来）；不传递（A 是 B 的 friend、B 是 C 的 friend ≠ A 是 C 的 friend）；进阶补充：不被继承（friend 的子类拿不到权限）。另一条便利：friend class 声明兼作前置声明——friend 前不用再写 class Display;（对比：friend 非成员函数用到未定义类型时需要前置声明）。

判断② "A 是 B 的 friend，B 是 C 的 friend，所以 A 能访问 C 的 private 成员。"

友元成员函数：精确到单个函数的授权

📐 概念：friend member function 与顺序难题

只想发一把钥匙而不是整个钥匙串？把单个成员函数设为 friend：friend void Display::displayStorage(const Storage& storage);。代价是一个顺序难题——编译器解析这条 friend 声明时，必须先见过 Display 的完整类定义（要知道 displayStorage 确实是它的成员）；而 Display 的函数定义又要访问 Storage 的成员，必须见过 Storage 的完整定义。官方解法（单文件四步）：

class Storage;                    // ① 前置声明 Storage（Display 里要用 const Storage&）

class Display
{
public:
    void displayStorage(const Storage& storage); // ② 只声明，不定义
};

class Storage
{
    // ...
    friend void Display::displayStorage(const Storage& storage); // ③ friend 声明
};

void Display::displayStorage(const Storage& storage)  // ④ 定义放最后
{ /* 访问 storage.m_nValue ... */ }

口诀：类的前置声明满足"引用这个类"；访问成员需要完整定义。多文件工程里每类一对 .h/.cpp，顺序自然解开（15.1 课的组织方式）。

选择③ 写 friend void Display::displayStorage(...) 之前，编译器必须已经见过什么？

ref 限定符（ref qualifiers）：选修

📐 概念：& / && 限定的成员函数重载（C++11）

14 章留过一个尾巴：返回 const std::string& 的 getter，隐式对象是 rvalue 时引用会悬垂（const std::string& ref { createEmployee("Garbo").getName() }; 之后用 ref 是 UB——rvalue Employee 已销毁）。ref 限定符允许按"隐式对象是 lvalue 还是 rvalue"重载成员函数：

const std::string& getName() const &  { return m_name; } // 只匹配 lvalue 对象
std::string        getName() const && { return m_name; } // 只匹配 rvalue 对象（拷贝走）

joe.getName();                     // joe 是 lvalue → 走 & 版（返回引用，零拷贝）
createEmployee("Frank").getName(); // 临时对象是 rvalue → 走 && 版（返回拷贝，不悬垂）

规则：同一函数的无限定版本与限定版本不能共存（二选一）；只有 const & 版时 lvalue/rvalue 都能调（const 左值引用可绑 rvalue，12 课）；限定版本可 = delete。官方立场：不推荐日常使用——为每个 getter 加 rvalue 版太啰嗦，防的是靠"立即使用返回值"就能避免的误用。了解即可，见到不慌。

判断④ "ref 限定符是官方推荐的最佳实践，每个返回引用的 getter 都应该配上 & 和 && 两个版本。"

💭 第 15 章收官：类是作用域，也是权限的主人

三课连起来看，第 15 章讲的其实是同一件事——类是一个作用域，作用域的主人掌握一切授权：this 指针揭示成员函数通过作用域找到对象；Date::、嵌套类型、静态成员都是"作用域里的居民"；friend 则是作用域主人签发的访问许可证（不互惠、不传递、不被继承——授权永不扩散）。下一章终于回到"用"的层面：标准库的动态数组 std::vector——你已经具备读懂它实现（类模板 + 静态成员 + 嵌套类型）的全部知识。
