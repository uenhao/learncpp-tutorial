2.4 前向声明与定义：先承诺后兑现

2.1 课的坑现在来填：为什么 a() 调用后面定义的 c() 会编译失败？因为编译器自上而下、逐行工作——它读到调用处时还不知道 c 存在。这一课给出解法，并引出 C++ 组织代码的核心机制。

📐 概念：声明 vs 定义

声明（declaration）：告诉编译器"存在一个叫这名字的函数，长这样"——带分号，没有函数体。

int add(int x, int y);   // 前向声明：一个承诺

定义（definition）：声明 + 函数体（真正实现）。

int add(int x, int y) { return x + y; }   // 定义：兑现承诺
#include <iostream>

int add(int x, int y);          // ① 承诺：存在这样的函数

int main()
{
    std::cout << add(3, 4);     // ② 编译器看过承诺，放行！
    return 0;
}

int add(int x, int y)           // ③ 兑现：真正的实现
{
    return x + y;
}

为什么编译器"信一个承诺"就够？回顾第 0.1 课：编译器只需要生成"跳转到 add"的机器码，add 到底在哪，链接器负责对接。声明给了编译器检查调用合法性的全部信息（参数类型、返回类型）；定义的位置它根本不关心。

One Definition Rule：承诺可以重复，兑现只能一次

📐 ODR（One Definition Rule）
  • 声明：同一文件里可以重复任意次
  • 定义：整个程序里只能有一次

重复定义会怎样？每个 .cpp 独立编译可能都通过，但链接器合并时发现两份同名实现，报 multiple definition。

判断"两个 .cpp 文件各自定义了 int helper(int)（实现完全相同），因为实现一样，所以不会出问题。"

签名：函数的"身份证号"

声明和定义要"对得上"。对得上什么？函数名 + 参数类型列表（合称签名 signature）。返回类型不算签名的一部分，但声明和定义的返回类型也必须一致（编译器会查）。

int add(int x, int y);        // 声明
double add(int x, int y)      // ❌ 返回类型不一致：编译错误
{ return x + y; }

int add(int a, int b)         // ✅ 形参名可以不同（a/b vs x/y），
{ return a + b; }             //    签名只看类型：int(int,int)
⚠️ 反例：手抄声明的灾难

假设 5 个 .cpp 都要调用 add，你手抄了 5 遍声明。某天 add 的签名改成 long add(long, long)，改漏了一个文件——那个文件继续按旧签名调用，编译通过、链接通过、运行时参数被错误解释。抄写是错误之源，声明应该只写一次、处处引用——这正是头文件（2.5 课）要解决的问题。先在这里埋下动机。

选择前向声明解决的是哪个问题？

💭 思维转变：从"顺序书写"到"接口优先"

有了前向声明，代码的物理顺序不再等于逻辑顺序——你可以把 main 放最上面（读者最先看到程序做什么），实现细节放后面。更进一步：先写声明（接口），后写实现成为设计手法：声明列表就是程序的"目录"。2.5 课的头文件把这个目录独立成文件，是同样的思想往前一步。

🎯 预测输出：

int triple(int x);   // 前向声明

int main() { std::cout << triple(4); }

int triple(int x) { return 3 * x; }
