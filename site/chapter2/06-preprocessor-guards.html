2.6 预处理器与头文件保护

你已经用过 #include 很多遍了，但"# 开头的行到底是什么、被谁处理"还没有正面回答。本课补全这块拼图，并解决头文件机制自带的一个必然问题。

预处理器：编译前的文本编辑器

📐 概念

预处理器（preprocessor）：编译前的独立步骤，对源码做纯文本处理。它不懂 C++ 语法、不懂变量、不懂类型——它只认识以 # 开头的指令，和"查找替换"这一件事。

指令作用现代 C++ 的替代品
#include粘贴文件内容（无，仍是标配）
#define MAX 30文本替换宏constexpr 变量
#if 0 ... #endif条件裁剪代码if constexpr / 版本管理
#ifndef X头文件保护#pragma once（非标准）

宏是纯文本替换，意味着它没有类型、没有作用域、会按字面展开——陷阱丛生：

#define SQUARE(x) x*x

SQUARE(3 + 1)
// 预处理后：3+1*3+1   →  3+3+1 = 7 ！！（你想要 16）
✅ 现代姿势：能用语言就用语言，宏只留给保护
constexpr int square(int x) { return x * x; }   // 有类型、可调试、无陷阱
square(3 + 1)   // 16，稳

头文件保护：粘贴机制的必然漏洞

先看一个会出问题的项目。它有 4 个文件，都很短——先自己读一遍，特别注意每个头文件的 #include 行：

// config.h —— 每个人都需要的公共声明
int getConfigValue();
// a.h —— 用到了 config 里的东西
#include "config.h"

int alpha();
// b.h —— 同样需要 config
#include "config.h"

int beta();
// main.cpp —— 同时使用 a 和 b
#include "a.h"
#include "b.h"

int main()
{
    return alpha() + beta() + getConfigValue();
}

main.cpp 没有直接 include config.h，但 a.h 和 b.h 各自需要它。直觉上这很合理——直到你想起 0.1 课说的：#include 是预处理器执行的复制粘贴。把流程画出来：

main.cpp
#include a.h → 拷入 config.h
#include b.h → 又拷入 config.h！

逐步拆开这次"灾难现场"：

  1. main.cpp 开始预处理——预处理器从上到下扫描 main.cpp，遇到 #include "a.h"。
  2. 拷入 a.h——a.h 的内容被原样粘贴到 include 处。粘贴进来的内容里也有 #include "config.h"，预处理器照章办事，继续追进去，把 config.h 的内容也粘贴进来（第 1 份）。
  3. 拷入 b.h——回到 main.cpp 继续扫描，遇到 #include "b.h"，同样粘贴。b.h 里又有一行 #include "config.h"——预处理器不记得刚才已经粘过它，于是再粘一遍（第 2 份）。

结果：预处理结束的翻译单元里，int getConfigValue(); 这行声明出现了两遍。#include 就是复制粘贴，它不做任何"去重"。声明重复两遍尚且无害（声明允许重复），但如果 config.h 里放的是定义——比如顺手写了个内联常量或函数体——重复粘贴就是真·重复定义，编译器直接报 redefinition。

📐 概念：头文件保护（header guard）

解法：给 config.h 套上保护。修好后的 config.h 长这样：

#ifndef CONFIG_H      // 如果 CONFIG_H 还没被 #define 过
#define CONFIG_H      // 标记：本次包含已发生

int getConfigValue(); // ...头文件的全部内容...

#endif                // 第二次进入时 CONFIG_H 已存在，内容被整体跳过

机制：宏"是否被定义过"被当成"这个文件是否已包含过"的标记。命名约定：全大写_文件名_H，全项目唯一。

选择main.cpp 没有直接 include config.h（只 include 了 a.h 和 b.h），但 config.h 的内容还是进来了两遍。为什么？

⚠️ 保护宏名写重了会怎样

两个不同的头文件都写成 #define UTILS_H：第一个被包含后，第二个的内容被整体跳过——它声明的函数"神秘消失"，报出一堆莫名其妙的 not declared。所以约定要全项目唯一（或用 #pragma once，非标准但所有主流编译器支持，没有起名负担）。

判断"#define ANSWER 42 定义的常量有类型检查，比 constexpr int 更安全。"

💭 思维转变：理解机制，而非背诵咒语

#ifndef/#define/#endif 是初学者最容易"抄了但不懂"的三行。但你现在能推导它：include=粘贴 → 多次包含=多次粘贴 → 需要"只粘贴一次"的标记 → 宏恰好能当标记。**每一条"必须这么写"的咒语背后都有一条可以推导的机制链**——遇到不懂的咒语，别背，问"它解决什么问题、没有它会怎样"。这是自学编程最重要的元技能。
