2.7 设计你的程序

第 1 章的"设计三问"在有了函数之后全面升级：现在你能把设计直接映射到代码结构上了。这一课先讲 learncpp 的完整设计方法（它其实是 7 步，不是 3 问），再用一个完整例子走完"从想法到能跑的代码"的全过程——这次有真代码、有参考答案。

完整的 7 步设计法（learncpp 2.13 原文）

原文把"设计"拆成 5 个设计步骤 + 3 个实现步骤。前 3 步对新手可以快进，但后 5 步是每天都在用的核心功：

阶段步骤做什么
设计① 定义目标用一两句话说清程序做什么（用户视角的成果）
② 定义需求列约束与能力清单——注意说"要什么"，不说"怎么做"
③ 工具/目标/备份新手可快进：自己用、单人、本机开发。但要记得备份代码（用 git）
④ 拆解难题把大任务拆成小任务，直到每块都不难（自顶向下）
⑤ 排出事件顺序把子任务串成执行顺序——这就是 main 的雏形
实现⑥ 写 main 骨架把顺序写成一行行被注释的函数调用
⑦ 逐个实现函数每写完一个函数就编译、测试，通过再写下一个
（收尾）整体测试 → 保持简单 → 逐步加功能 → 定期重构
📐 步骤④的关键：任务层级（原文的"打扫房子"例子）

"打扫房子"太大没法下手，拆：

打扫房子
├── 吸地毯
├── 打扫浴室
│   ├── 刷马桶
│   └── 洗洗手池
└── 打扫厨房
    └── 倒垃圾

拆到每一片叶子都"不难"为止。程序设计同理："写个温度转换器"不好下手，拆成"读输入 / 做换算 / 打印结果"，每一块才对应得上具体的函数。原文还提到自底向上的反方向：先列一堆会做的小事，再把它们归组——两种方向都能建立任务层级。

📐 步骤⑥⑦的关键：先骨架后填肉（原文的"计算器"例子）

把步骤⑤的事件顺序直接翻译成 main 的注释骨架：

int main()
{
    // 从用户获取第一个数
    // getUserInput();

    // 获取运算符
    // getMathematicalOperation();

    // 获取第二个数
    // getUserInput();

    // 计算结果
    // calculateResult();

    // 打印结果
    // printResult();

    return 0;
}

然后一次只实现一个函数：定原型（输入输出是什么）→ 写函数体 → 在 main 里加临时代码测试它 → 通过后删掉临时代码、解锁下一个调用。原文的原话值得记住："不要一口气写完整个程序。一步一步来，每步都测试后再前进。"

✅ 原文给新手的四条忠告
  • 从最简单的版本开始："带图形音效随机地下城的 RPG"只会让你崩溃；先写"在屏幕上显示一个二维格子"
  • 随时间增加功能：格子 → 会走路的角色 → 墙 → 小镇 → 商人
  • 一次加一个功能，每个功能都是"先让它在现有基础上工作"
  • 随时重构：消除重复、拆长函数——可维护性优先于炫技

实战：温度转换器（完整走一遍 7 步）

下面把上面的方法原样套在一个小项目上。这个例子在仓库 chapter2/13-design-first-programs/temperature/ 有完整可编译的代码，网页里的每一步都与仓库文件一一对应。

第①步：定义目标

一句话："允许用户输入一个温度和单位（F 或 C），程序输出换算成另一种单位后的温度。"

第②步：定义需求

  • 用户输入一个数字和一个单位字母（如 100 C 或 32 F）
  • 程序按正确的公式换算并打印结果
  • 输入了 F/f 或 C/c 之外的东西，要给出可理解的提示而不是乱输出
  • （说"要什么"不说"怎么做"——注意上面没有任何一句提到函数或文件）

第③步：工具/目标/备份

本机 g++ + VS Code，单人自用。备份：本项目就是 git 仓库（如果还没有，git init 一下，学编程第一天就该有这个习惯）。

第④步：拆解

温度转换器
├── 换算：华氏 → 摄氏
├── 换算：摄氏 → 华氏
├── 用户交互：读入温度与单位
└── 用户交互：打印结果

第⑤步：事件顺序

读入温度和单位
判断单位
  若 F：调用华氏→摄氏，打印
  若 C：调用摄氏→华氏，打印
  否则：打印错误提示

第⑥步：main 骨架

int main()
{
    // 读入温度与单位
    // readInput();

    // 判断单位并换算、打印
    // convertAndPrint();

    return 0;
}

第⑦步：逐个实现

先实现两个纯换算函数（它们不碰 cin/cout，最好测）。华氏转摄氏的公式是 C = (F − 32) × 5 ⁄ 9：

// convert.h —— 先写"契约"
#ifndef CONVERT_H
#define CONVERT_H

// Converts a Fahrenheit temperature to Celsius.
double fahrenheitToCelsius(double fahrenheit);

// Converts a Celsius temperature to Fahrenheit.
double celsiusToFahrenheit(double celsius);

#endif
// convert.cpp —— 再写"兑现"
#include "convert.h"

double fahrenheitToCelsius(double fahrenheit)
{
    return (fahrenheit - 32.0) * 5.0 / 9.0;
}

double celsiusToFahrenheit(double celsius)
{
    return celsius * 9.0 / 5.0 + 32.0;
}

立刻测试这两个函数（第⑦步要求每写完一个就测）：写个五行的临时代码调一下——

// 临时测试代码（测完就删）
#include <iostream>
#include "convert.h"

int main()
{
    std::cout << fahrenheitToCelsius(212.0) << '\n'; // 期待 100
    std::cout << celsiusToFahrenheit(100.0) << '\n'; // 期待 212
    std::cout << fahrenheitToCelsius(32.0)  << '\n'; // 期待 0
    return 0;
}
g++ -std=c++20 -Wall -Wextra -I. -o t convert.cpp test.cpp && ./t
100
212
0          ✅ 公式正确，可以进入下一步

换算层确认可靠后，再实现交互层：

// main.cpp
#include <iostream>
#include "convert.h"

int main()
{
    std::cout << "Enter temperature and unit (F or C), e.g. 100 C: ";

    double temp{};
    char unit{};
    std::cin >> temp >> unit;

    if (unit == 'F' || unit == 'f')
        std::cout << temp << "F = " << fahrenheitToCelsius(temp) << "C\n";
    else if (unit == 'C' || unit == 'c')
        std::cout << temp << "C = " << celsiusToFahrenheit(temp) << "F\n";
    else
        std::cout << "Unknown unit: " << unit << '\n';

    return 0;
}

第⑦步的收尾：整体测试

输入期待输出检验了什么
100 C100C = 212F常规换算
32 F32F = 0C冰点边界
-40 C-40C = -40F两标度相等的特殊点（负数处理）
50 XUnknown unit: X非法输入分支
🧩 设计取舍：为什么换算逻辑单独放 convert.h/convert.cpp，而不直接写在 main 里？

把"会变的东西"（交互方式）与"稳定的东西"（数学公式）分开。今天用 cin，明天换 GUI、后天做成库给别人用——convert.h 一个字都不用改。此外分离后换算函数可以不启动 UI 单独测试（上面那五行临时代码就是证明），也可以被别的程序 include 复用。对照仓库的 temperature/ 三件套亲自编译跑一遍：

cd chapter2/13-design-first-programs/temperature
g++ -std=c++20 -Wall -Wextra -I. -o temp main.cpp convert.cpp
./temp        # 试 100 C、32 F、-40 C、50 X 四个用例

选择把换算逻辑放进独立函数/独立文件，最大的收益是？

选择第⑦步说"每实现一个函数就立刻测试"。如果不这么做，一口气写完全部五个函数才第一次编译运行，最可能的后果是？

💭 思维转变：先设计后编码，伪代码是脚手架

注意整个实战里，真正敲 C++ 代码之前发生了什么：一句话目标 → 需求清单 → 任务树 → 事件顺序 → 注释骨架。这些中间产物看起来"很慢"，但它们把你从"面对空白文件不知道写什么"的瘫痪状态里解放出来——写 convert.h 时你只需要照着任务树上的"换算：华氏→摄氏"这一片叶子工作，其他什么都不用想。learncpp 作者的忠告：写程序最难的部分不是敲代码，而是在敲代码之前想清楚。等这套流程熟练之后，你会逐渐能"边写边设计"——但那是长在扎实流程上的自由，不是跳过流程的莽撞。
