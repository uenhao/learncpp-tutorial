3.2 调试流程：六步走

场景：程序编译通过，运行起来却给出错误结果——必然存在某个运行时语义错误。怎么找？

📐 所有 bug 的共同前提

每个 bug 都源于一个简单的事实：你原以为正确的某件事，其实是错的。

如果你平时坚持"写一点测一点"（第 2.7 课的方法论），你大概知道问题在哪；如果完全没有头绪——这一课就是为你准备的。

六步调试流程

① 找根因
② 理解成因
③ 确定修法
④ 修复
⑤ 复测修复
⑥ 复测无新伤
  1. 找到问题的根因（root cause）——通常是那行"没按你想的工作"的代码。这是六步中最难的一步（3.3 课专门讲策略）。
  2. 弄清问题为什么发生——不理解成因就动手改，等于掷骰子。
  3. 确定怎么修——可能有好几种修法（改代码 / 绕过去 / 换方案）。
  4. 实施修复。
  5. 复测：确认问题已修复。
  6. 复测：确认没有引入新问题——修复本身也可能带 bug。

生活案例：坏了的制冰机（原文类比）

晚上你想接冰块，按下制冰机把手——什么都没出来。用六步走一遍：

  • 找根因：机器在"努力"出冰（有声音），说明出冰机构多半没坏。开冰箱检查冰盒——空的。这是根因吗？不是，这只是另一个症状。继续查：冷冻室够冷、水管没堵、其他都正常 → 结论：根因是制冰机坏了。
  • 理解问题：坏的制冰机当然不出冰。简单。
  • 确定修法：选项包括绕过去（去便利店买袋装冰）、继续深挖修零件、换制冰机、换整个冰箱。权衡后决定：换制冰机。
  • 修复：装上新的。
  • 复测：通电过夜后，冰做出来了。
  • 复测无新伤：没发现新问题。
⚠️ 症状 ≠ 根因

上面最关键的一步是识别出"冰盒是空的"只是症状而非根因。修 bug 时最常见的浪费是：盯着症状改代码——输出错了就改 cout 那一行，实际上错在十行之外的赋值。症状是 bug 的下游表现；根因才是要修的东西。六步流程的第一步之所以最难，就是因为要逆流而上找源头。

实战：回到 3.1 的减法冒充加法案

#include <iostream>

int add(int x, int y) // 本该做加法
{
    return x - y;     // 手滑
}

int main()
{
    std::cout << "5 + 3 = " << add(5, 3) << '\n'; // 应输出 8，实际输出 2
    return 0;
}

这个案子好在：错误结果直接打印在屏幕上（第 10 行），给了一个调查起点。走六步：

  1. 找根因：第 10 行传的是字面量 5 和 3——输入不可能错；输入对而输出错，问题必然在 add 内部。add 里只有一条 return 语句——锁定它。顺着看下去，减号写成加号的意图很容易发现。
  2. 理解问题：用错了运算符，显而易见。
  3. 确定修法：operator- 改成 operator+。
  4. 修复：改掉它，确保重新编译通过。
  5. 复测：重跑，输出 8，正确。
  6. 复测无新伤：对这个小程序而言，到此为止。

判断"调试六步中最耗时的通常是'修复'那一步——找到问题之后改代码很快。"

选择程序打印出的金额总是比期望少。你的同事说："打印金额的那行 cout 我看了没问题，要不把 % 换成别的试试？"按照六步流程，下一步该做什么？

💭 思维转变：调试是侦查，不是猜谜

新手调试的动作往往是"改一下试试"——这是猜谜。六步流程把调试变成侦查：观察症状 → 收集线索 → 收敛到根因 → 确认动机 → 修复 → 验证。每一环都有证据支撑。区别在哪？猜谜的人修完一个 bug 心里没底；侦查的人修完能说清楚"为什么错、为什么这样改、为什么别的功能不受影响"。从本章起，请用"我找到了根因，证据是……"的句式向自己汇报。
