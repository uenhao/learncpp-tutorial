3.3 定位策略：代码审查与 hi-lo 收敛

上一课说：调试的大部分时间花在"找到错误在哪"。这一课讲两条定位路径：靠看（代码审查）和靠跑（运行程序收集线索）——以及从后者提炼出的 hi-lo 收敛策略。

路径一：代码审查（code inspection）

📐 概念

代码审查定位：根据错误的性质和程序结构，推断问题最可能藏在哪个函数里，然后盯着那段代码看。

int main()
{
    getNames();  // 让用户输入一堆名字
    sortNames(); // 按字母序排序
    printNames(); // 打印排序后的名单
    return 0;
}

预期"按字母序打印"，实际却"逆序打印"——三个函数里谁最可疑？显然是 sortNames。能收敛到一个函数时，肉眼审查往往直接命中。

但审查有四个天然局限：

  • 代码量大：几千行逐行看，又慢又枯燥；
  • 代码复杂：出错的可能位置太多；
  • 线索缺失：程序什么都不输出时，连"从哪看起"都不知道；
  • 最致命的——坏假设：如果 bug 是由一个错误假设造成的，你审查时会犯同样的错误假设，于是对着那行代码看十遍也看不出错。你想的和代码做的是同一件错事。

判断"只要足够仔细，盯着代码看总能发现所有 bug。"

路径二：运行程序收集线索

📐 概念：通用三步循环
  1. 重现问题（reproduce）
  2. 运行程序，收集信息，缩小怀疑范围
  3. 重复上一步，直到锁定问题

第一步：重现问题

能稳定重现是定位的第一前提——无法观察到的错误几乎无法诊断。回想制冰机：朋友说"你家的制冰机坏了"，你过去一看，好好的——这怎么诊断？只有当你亲眼看到"不出冰"，调查才能展开。

明显的 bug（每次运行都在同一处崩溃）天然可重现；麻烦的是"只在某些机器 / 某些输入下出现"的 bug。此时要整理重现步骤（reproduction steps）：一串清晰、精确、可高概率复现问题的操作序列。理想是 100% 重现；哪怕只有 50%，也只是诊断时间翻倍——最糟的是无法重现，线索直接断掉。

第二步：hi-lo 收敛法

重现了问题、但完全不知道 bug 在哪，怎么办？原文用了 hi-lo 猜数游戏的类比：猜 1–10 之间的数，每次猜完只告诉你"太大 / 太小 / 正确"。用最优策略，最多 4 次就能锁定——不需要遍历所有可能，每次猜测都会给你排除一半空间的信息。

调试同款策略。关键事实：bug 必然位于"程序开始执行"到"第一次出现可观察症状"之间的代码里——症状之后的部分先排除。然后做有依据的猜测：

📐 两种"猜测结果"的判读
  • 能证明"这一刻问题还没发生" → 相当于"太小"：bug 在更靠后的代码里。例：程序每次都在同一处崩溃；在崩溃点之前的某处检查过、确认状态正常 → 往后找。
  • 观察到与问题相关的错误行为 → 相当于"太大"：bug 在更靠前的代码里。例：程序打印变量 x，期望 2 却打印 8；在运行途中发现 x 此时已经是 8 → 往前找（x 被污染发生在你看它之前）。

有时还能整段排除代码而不产生方向信息（比如注释掉一个显然无关的函数）——这同样缩小包围圈。

猜得足够多次、方法得当，包围圈就收敛到一行代码。到那时，"理解为什么"往往一眼即穿——而且这个过程会顺带暴露你的坏假设（你猜错了方向，说明你的假设和现实不符）。

选择程序把用户的存款余额显示为 999999，正确值应为 500。你在"读取账户"之后加了检查，余额此时仍是正确的 500；在"显示余额"之前又检查了一次，此时已经变成 999999。按 hi-lo 策略，结论是？

💭 思维转变：把"找不到 bug"转化为"缩小包围圈"

"这个程序几千行，bug 在哪？"这个问题令人绝望；"bug 在这两行之间，怎么缩小？"这个问题可解。hi-lo 策略的本质是用信息换空间：每次观察（哪怕只是"这里还正常"）都在砍掉一半的嫌疑代码。所以调试时别问"哪里错了"，问"我能做什么观察、能把包围圈砍掉多少"。下一课的具体战术（注释代码、打印流程、打印值）全都是"做观察"的手段；3.6–3.9 的调试器则是让观察变便宜的工具。
