3.4 基础调试战术：注释、流程验证、打印值

3.3 课说定位靠"猜测 + 收集信息"。这一课讲三个手动做"猜测"的具体战术。它们朴实无华，却在你没有调试器或程序必须跑在别处时是唯一选择。

战术一：注释掉代码（commenting out）

程序行为异常，把部分代码注释掉再运行——问题依旧，说明被注释的部分多半无辜；问题消失，锁定嫌疑人。

int main()
{
    getNames();      // 输入名字
//    doMaintenance(); // 一些杂事 —— 注释掉试试
    sortNames();     // 排序
    printNames();    // 打印
    return 0;
}

三种可能结果：

  1. 问题消失 → doMaintenance 就是元凶，火力集中到它；
  2. 问题不变（更常见）→ doMaintenance 基本排除，至少这几行不用再看了；
  3. 问题变形（比如名字不打印了）→ doMaintenance 在提供别的代码依赖的东西，暂时排除不了——恢复它，换战术。
⚠️ 别忘了恢复注释掉的代码！

调试改了很多处之后，漏掉一两处没恢复是常事——结果修好一个 bug 又亲手引入新的。原文给的两条护栏：① 用版本控制（git diff 一眼看清所有调试期改动）；② 用 3.5 课的 #ifdef 条件编译替代反复注释。

战术二：验证代码流程（validating flow）

另一类常见 bug：函数被调用的次数不对（太多、太少、压根没调）。在函数入口打印函数名，运行后一目了然：

#include <iostream>

int getValue()
{
std::cerr << "getValue() called\n";   // 调试语句：故意不缩进，方便日后删除
	return 4;
}

int main()
{
std::cerr << "main() called\n";
    std::cout << getValue << '\n';    // 有 bug！
    return 0;
}

运行输出：

main() called
1

getValue() called 没出现！函数从未被调用——问题出在调用处。凑近看：getValue 后面漏了括号，打印的是函数指针而不是调用结果。补上括号，输出立刻正确：

main() called
getValue() called
4
📐 概念：为什么调试输出用 std::cerr 而不是 std::cout

std::cout 是带缓冲的：你让它输出的文字可能先攒在缓冲区，稍后才真正写到屏幕。如果程序在输出前崩溃，缓冲区内容会丢失——你看到的"最后一条输出"可能骗你（它后面的代码其实执行过）。std::cerr 是无缓冲的：发出去立刻显示，绝不迟到。调试时我们要的是"每个观察都准时"，性能损失无所谓。这也是原文的明确规则：调试输出一律用 std::cerr。

✅ 临时调试语句故意不缩进

上面调试行顶格写（无缩进）不是手滑——是让它们在代码里一眼可辨，方便日后统一删除（如果用 clang-format 自动格式化，会被缩进"隐藏"掉，需要 // clang-format off 保护）。

战术三：打印值（printing values）

最常用的战术：怀疑哪个变量/表达式的值，就把它打印出来看。完整走一遍原文的案例：

#include <iostream>

int add(int x, int y)
{
	return x + y;
}

void printResult(int z)
{
	std::cout << "The answer is: " << z << '\n';
}

int getUserInput()
{
	std::cout << "Enter a number: ";
	int x{};
	std::cin >> x;
	return x;
}

int main()
{
	int x{ getUserInput() };
	int y{ getUserInput() };

	int z{ add(x, 5) };   // ← bug 藏在这里
	printResult(z);

	return 0;
}

运行（输入 4 和 3）：

Enter a number: 4
Enter a number: 3
The answer is: 9        ← 应该是 7！

肉眼不好找。给每个关键变量加打印：

	int x{ getUserInput() };
std::cerr << "main::x = " << x << '\n';
	int y{ getUserInput() };
std::cerr << "main::y = " << y << '\n';

	int z{ add(x, 5) };
std::cerr << "main::z = " << z << '\n';
	printResult(z);

输出变成：

Enter a number: 4
main::x = 4
Enter a number: 3
main::y = 3
main::z = 9        ← x、y 都对，z 从这里就开始错
The answer is: 9

x、y 正确而 z 错误 → 问题必然在"由 x、y 算出 z"这一步，也就是 add。给 add 加入口打印：

add() called (x=4, y=5)    ← 传入的 y 是 5！但 main 里 y 是 3

真相大白：回头看调用行 int z{ add(x, 5) };——第二个实参写成了字面量 5，本该是变量 y。修复、删调试语句、收工。

进阶案例：入口打印抓"提前修改"

另一个几乎相同的程序，输出 4+3=5。加全套调试后：

main() called
getUserInput() called
Enter a number: 4
main::x = 3        ← 用户输入 4，x 却是 3！
getUserInput() called
Enter a number: 3
main::y = 2        ← 同样少 1
...

问题出在"用户输入 → main 的 x"之间。给 getUserInput 内部再加一行打印：getUserInput::x = 4——函数内 x 是对的，返回到 main 却少了 1。包围圈收到最后一行：return --x; 里的 --（自减，你此刻还没学过，但不认识它不妨碍你锁定它是嫌疑人——这就是 hi-lo 的威力）。删掉 --，程序正确。

打印调试的局限

原文对打印调试的四条批评，值得记住（它们是 3.6 起调试器存在的理由）：

  1. 调试语句弄脏代码；
  2. 调试输出弄脏程序输出；
  3. 加/删调试语句要改代码，可能引入新 bug；
  4. 用完必须删，不可复用。

选择调试输出应该用 std::cerr 的根本理由是？

判断"用打印法定位 bug 时，只要给所有变量都加上打印，就一定最快找到问题。"

💭 思维转变：调试语句是"探针"，位置比数量重要

三个战术其实是同一个动作的三种形态：把程序的内部状态暴露出来供你观察。注释法暴露"这段代码是否影响行为"，流程打印暴露"执行路径长什么样"，值打印暴露"数据在哪一步开始变错"。原文案例最精彩的地方：那行 return --x; 里的 -- 是个你还不会的语法，但你依然不需要懂它就能锁定它——探针给出的是客观行为证据，不依赖你的理解是否正确。这恰好补上了 3.3 课说的"坏假设是审查盲区"的洞。
