3.5 进阶调试战术：条件编译与日志

3.4 课结尾批评了打印调试的四条缺点。这一课用两个进阶战术缓解它们——而它们恰好用到你已经学过的知识：预处理器（2.6 课）。

战术四：用条件编译开关调试语句

3.4 的打印法有个恼人的循环：调试 → 删语句 → 又出 bug → 再加回来 → 再删……用预处理器把这个循环自动化：

#include <iostream>

#define ENABLE_DEBUG // 注释掉这一行即可关闭所有调试输出

int getUserInput()
{
#ifdef ENABLE_DEBUG
std::cerr << "getUserInput() called\n";
#endif
	std::cout << "Enter a number: ";
	int x{};
	std::cin >> x;
	return x;
}

int main()
{
#ifdef ENABLE_DEBUG
std::cerr << "main() called\n";
#endif
    int x{ getUserInput() };
    std::cout << "You entered: " << x << '\n';
    return 0;
}
📐 机制回顾：#ifdef 在做什么

2.6 课的头文件保护就是 #ifndef：宏没被定义过才保留内容。这里的 #ifdef ENABLE_DEBUG 反过来：宏被定义过才保留内容。预处理器在编译前把 #ifdef/#endif 之间的代码"保留"或"整体抹掉"——被抹掉的代码从未参与编译，不是运行时跳过。所以关闭调试后，程序和没写过这些语句一模一样，零运行时开销。

收益与代价：

  • ✅ 调试语句可保留在代码里，随时一行开关，不怕删错、不怕重加；
  • ✅ 多文件项目里把 #define ENABLE_DEBUG 放进头文件，一处开关全局生效；
  • ❌ #ifdef/#endif 让代码更乱了（两行包裹一行）；
  • ❌ 宏拼写错误或头文件漏 include，某些文件的调试会静默失效。

战术五：日志（logging）

📐 概念

日志（log）：程序运行过程中发生的事件的顺序记录（通常带时间戳），写到日志文件里。写日志的过程叫 logging。

和打印法相比的两个本质改善：① 调试信息与程序输出分离——屏幕不再被刷屏；② 日志文件可以发给别人——用户机器上出了问题，让他把日志发给你，远程诊断成为可能。

C++ 标准库自带 std::clog，但它默认仍写到标准错误流，想落盘还得自己重定向。实际项目一般用现成的第三方日志库。原文演示了 plog（header-only，即只有头文件、拿来即用——2.5 课头文件机制的延伸）：

#include <plog/Log.h>   // 第 1 步：包含日志库头文件
#include <plog/Initializers/RollingFileInitializer.h>
#include <iostream>

int getUserInput()
{
	PLOGD << "getUserInput() called";  // PLOGD 由日志库定义

	std::cout << "Enter a number: ";
	int x{};
	std::cin >> x;
	return x;
}

int main()
{
	plog::init(plog::debug, "Logfile.txt"); // 第 2 步：初始化（文件名+级别）

	PLOGD << "main() called";               // 第 3 步：像 cout 一样写

	int x{ getUserInput() };
	std::cout << "You entered: " << x << '\n';
	return 0;
}

运行后 Logfile.txt 里出现：

2018-12-26 20:03:33.295 DEBUG [4752] [main@19] main() called
2018-12-26 20:03:33.296 DEBUG [4752] [getUserInput@7] getUserInput() called

时间戳、进程号、函数名、行号全自动。关闭日志也不用动调试语句：把 init 改成 plog::none 即可——没有 #ifdef 包裹，代码保持干净。日志库很多（性能敏感的大项目常用 spdlog），选型随意，思想一致。

⚠️ 本课的两个战术都不是终点

条件编译解决了"可复用"，日志解决了"输出分离 + 远程诊断"，但它们依旧要在代码里写语句、改代码。真正的升级是：不修改代码就能观察程序内部——这正是集成调试器的领地（3.6–3.9 课）。原文的顺序很清楚：打印法 → 条件编译/日志 → 调试器，工具越往后越强、对代码的侵入越少。

💭 思维转变：调试基础设施是一种投资

打印法是"一次性脚手架"——用完就拆；条件编译是"可折叠脚手架"——留着但碍事；日志是"永久基础设施"——建成之后每次出问题都受益，甚至能在用户没报 bug 时就发现异常。这是工程思维的缩影：重复出现的痛苦值得一次性投资去消除。学完本章你会发现同样的模式出现在调试器（一次学会，处处省时）、单元测试（一次编写，每次改代码都验证）上。第 3.10 课会把这条线索收尾。
