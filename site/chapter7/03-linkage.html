7.3 链接性：static、extern 与全局变量之恶

两个 .cpp 文件里各有一个 int g_x——链接器会把它们当同一个对象吗？答案取决于链接性。

internal vs external：一张表说清

📐 概念：全局变量与函数的两种链接性
链接性含义谁默认拥有
internal（内部）只在本翻译单元可见；两个文件同名 = 两个独立对象，不违反 ODRconst 全局变量、constexpr 全局变量
external（外部）跨翻译单元可见：文件 A 的声明可与文件 B 的定义对接（链接器对接）非 const 全局变量、函数

static 关键字把非 const 全局变量的链接性从 external 改成 internal。

static int g_internal{};   // 强制内部链接：其他文件看不见它
const int g_const{ 1 };    // 默认内部链接（const 全局）
constexpr int g_cexpr{ 2 };// 默认内部链接
extern int g_shared;       // 声明：定义在别的文件里（外链接）

extern：跨文件共享变量的声明（2.8 课机制的变量版）

📐 概念：extern 声明

函数有前向声明（2.4 课），全局变量也有：extern 声明告诉编译器"这个变量在别的翻译单元里定义"。链接时跨文件对接——与函数声明对接函数定义完全同构。

// globals.cpp —— 定义
int g_mode{ 4 };

// globals.h —— 声明（extern）
extern int g_mode;

// main.cpp —— #include "globals.h" 后直接用

注意：extern 声明处不要写初始化（写了就是重定义）；声明可多处，定义只能一处（ODR）——与函数的声明/定义规则一模一样。

非 const 全局变量是恶魔（原文原话）

3.9 课"制冰机"级的警告：全局变量任何函数都能改，而且读代码的人无从知道哪个调用会改：

int g_mode{};

void doSomething()
{
    g_mode = 2; // 谁能想到这个函数会动全局状态？
}

int main()
{
    g_mode = 1;
    doSomething();
    if (g_mode == 1)
        std::cout << "safe\n";
    else
        std::cout << "boom\n"; // 实际走这里
}
⚠️ 恶魔的三宗罪
  1. 不可追踪：值错了，要翻遍整个程序找是谁改的（3.3 课 hi-lo 的包围圈瞬间变成全程序）；
  2. 状态不可预测：每次函数调用都可能是"暗改"，程序行为依赖调用历史；
  3. 初始化顺序问题：跨文件的全局变量初始化顺序不确定——一个全局的初始化依赖另一个全局，就可能拿到未初始化的值。
✅ 原文最佳实践
  • 优先用局部变量，避免非 const 全局变量；
  • 需要"共享的量"？用参数传递把数据显式交给函数（谁改了什么一目了然）；
  • 全局常量（const/constexpr）是安全的——只读属性天然免疫"暗改"；跨文件共享见下一课的 inline 变量。

判断① "两个 .cpp 各定义了 static int g_count{0};，链接器会报重复定义。"

选择② 文件 A 定义 int g_score{ 0 };，文件 B 想用它。B 里该写？

💭 思维转变：链接性是"翻译单元的隐私设置"

2.8 课你学过"翻译单元是编译的基本单位、编译器不知道别的 .cpp 存在"。链接性就是翻译单元层面的隐私开关：internal = "本单元私有"（static/const/constexpr），external = "愿意跨单元共享"（默认）。ODR、头文件保护、extern 声明、static——这些散落的规则全部统一到这张图上。**命名空间是'作用域层'的隔离（2.9），链接性是'文件层'的隔离**——两层防线，各管一段。
