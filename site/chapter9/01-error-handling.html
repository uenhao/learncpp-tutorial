9.1 错误检测与处理：测试、cerr、assert

本章把第 3 章（调试）、3.10 课（防患于未然）、5.4 课（cin 失败）散落的"错误处理"线索收拢成体系。鲁棒（robust）的程序 = 预见了误用并优雅处理。

测试你的代码（9.1–9.2）

📐 概念：单元测试（unit testing）

3.10 课的 testadd() 就是单元测试雏形。测试的价值回顾：① 输入是精心挑选的已知答案；② 错误当场暴露；③ 可永久保留防回归。

代码覆盖率（code coverage）：测试执行了代码的百分之多少。语句覆盖 100% ≠ 没问题——每条语句都跑到过，不代表每个分支组合都验证过。原文建议：追求高覆盖率，但用已知 bug 的代码校准你对覆盖率的信任。

常见语义错误清单（9.3）

⚠️ 原文的"高频语义错误"清单（对照自查）
  • if 内执行了无限循环——条件变量忘了迭代；
  • 无符号溢出——4.5 课的"避免无符号"再论证；
  • 运算符优先级误解——6.1 课"拿不准加括号"；
  • 短路求值的误依赖——右操作数被跳过时遗漏了它应有的副作用；
  • switch 跌落——8.1 课的忘 break；
  • 调用未初始化的变量——1.4 课口诀"定义即初始化"；
  • 切片与窄化——4.12 课 static_cast 的纪律。

错误处理的四种策略（9.4）

📐 概念：函数失败时的四个选项
  1. 函数内自行处理（最好）：重试直到成功，或取消当前操作；
  2. 把错误传回调用者：返回值表达错误（如返回 false / -1 / 空串）——调用者决定怎么办；
  3. 终止程序：error() / std::exit / assert——错误致命且不可恢复时；
  4. 抛异常：错误无法在本地合理处理时——第 27 章展开。

"静默忽略"是第 1 种的劣化版——调用者完全无从知晓出了错，能加错误提示就加（std::cerr）。

std::cin 的失败处理（9.5）——5.4 课伏笔的完整解

📐 概念：提取失败机制与恢复三步

1.4 课的 "tom abc" 案例完整机制：提取失败 → 变量置 0（C++11）→ cin 进入失败状态 → 后续提取全部静默跳过。恢复三步：

#include <limits>

void ignoreLine()
{
    std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
}

double getDouble()
{
    while (true) // 循环直到拿到合法输入
    {
        std::cout << "Enter a decimal number: ";
        double x{};
        std::cin >> x;

        if (!std::cin)           // ① 判断失败（bool 转换）
        {
            std::cin.clear();    // ② 清除失败状态
            ignoreLine();        // ③ 丢掉坏输入行
            continue;            // 重试
        }

        ignoreLine();            // 成功也清掉行尾残留
        return x;
    }
}

Key insight（原文）：提取失败后，包括 ignore() 在内的一切提取都会静默失败——clear() 通常是恢复的第一步。ignoreLine 用 numeric_limits<streamsize>::max() 丢弃整行，比写死 100 个字符稳健。这就是 1.4 课"防御性输入"的完整答案，第 8 章 do-while 重试的实战化。

assert 与 static_assert（9.6）

📐 概念：运行时断言 assert（<cassert>）

断言：除非程序有 bug，否则必为真的表达式。为真 → 什么都不做；为假 → 打印文件名/行号/表达式并 std::abort 终止程序——让你立刻用调试器检查现场（第 3 章武器库直接上线）。

#include <cassert>  // assert
#include <cmath>

double calculateTimeUntilObjectHitsGround(double initialHeight, double gravity)
{
  assert(gravity > 0.0); // "除非程序有 bug，重力必为正" —— 参数校验

  if (initialHeight <= 0.0)
    return 0.0;

  return std::sqrt((2.0 * initialHeight) / gravity);
}
传 (100.0, -9.8) 时输出：
dropsimulator: src/main.cpp:6: ...: Assertion 'gravity > 0.0' failed.
⚠️ NDEBUG：发布版关闭断言

断言每次检查有性能开销，且理想中发布版不该触发（上线前已测完）。定义宏 NDEBUG 即整体禁用 assert——多数构建系统在 Release 配置自动定义。手动开关：#define NDEBUG（禁用）或 #undef NDEBUG（启用），放在所有 include 之前、行尾无分号。这也再次呼应 0.2 课 Debug/Release 的分工。

📐 概念：static_assert——编译期断言

static_assert(常量表达式, "消息")：在编译期检查，失败即编译错误。检查对象必须是常量表达式（constexpr 变量、字面量运算）——运行时值无法用它检查。适合验证"类型大小""平台假设"等编译期事实。

assert vs if：什么时候用哪个

assertif 错误处理

💭 思维转变：错误的"责任分层"

四种策略不是平级的菜单，而是一条责任链：能在本地修复就本地修复（不惊动别人）；修不了就带着信息上交（返回错误）；错误致命就立即终止（assert/exit）；只有"无法本地处理、又不该终止"的复杂错误才值得异常。选择的关键问题是：这个错误的合理处理者是谁？——谁有足够的上下文谁负责。这个思路在第 12 章（引用传递改造参数）和第 27 章（异常）会持续深化。
